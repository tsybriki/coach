1 · Схема подсистем

Операционный контур (Season → … → Step, факт, итог недели) закрыт в DOMAIN-SPEC.html. Здесь — только раскладка на подсистемы поверх него: кто принимает решение, кто хранит, кто приносит факт, кто отдаёт результат человеку.

планировщик — считает и принимает решения входные справочники состояние факт и оценка доставка пользователю нарратор — только текст

Подсистемы — соседи, связи помечены номерами; номера — таблица «Взаимодействия». Тонкая стрелка без наконечника — двусторонняя связь.

2 · Планировщик

Планировщик — единственная подсистема, которая принимает решения. Три входа: сезон, неделя, остаток недели.

Вход 1 · ЦЕЛЬ → МАКРОПЛАН
  1. Нормализовать цель: метрика + дата → целевой VDOT (Дэниэлс: 10К 40:00 → VDOT 52).
  2. Оценить текущую форму: факт 10К 44:06 → VDOT 46.4, тренируемся по 48. Разрыв 4–6 VDOT.
  3. Оценить потолок: сколько VDOT набирается за N недель при текущем объёме.
  4. Вердикт: достижима · достижима с оговорками · недостижима.
  5. При недостижимости — варианты: смягчить метрику · сдвинуть дату · наилучшая достижимая цель.
  6. Построить Plan: фазы, weekly targets, load budget, control points.
вход Goal (метрика + дата) + Профиль атлета
цифры Цель 10К 40:00 = VDOT 52 · факт 10К 44:06 = VDOT 46.4 · тренировочный 48 · гонка 18.04.2027 = W28 из 49
есть goal_guard.py проверяет согласованность плана с целью — но не достижимость цели из текущей формы.
нет Шаг 3 — модели потолка формы нет. Шаг 6 — генератора макро нет: weekly_macro (28 недель из 49) написан руками.
Вход 2 · МАКРО + НЕДЕЛЯ → ТРЕНИРОВКИ
  1. Взять цель и объём недели из макро.
  2. Выбрать структуру качественной сессии по (goal, scale).
  3. Разложить по слотам календаря.
  4. Что не разложилось — в unplaced: висяк, решение пользователя.
  5. Собрать шаги; длительность тренировки = Σ шагов.
  6. Неделя готова к активации — активация по команде пользователя.
вход макро (weekly target недели) + Профиль атлета + Среда (слоты)
цифры работает: plan_generate · step_builder · quality_session · workout_templates
есть lib/plan_generate.py + lib/step_builder.py + lib/quality_session.py + state/workout_templates.json — этот вход собран и работает.
нет Наследование слотов Season ← Phase ← Week не реализовано: слот берётся только из constraints.json.
Вход 3 · ОСТАТОК НЕДЕЛИ → ПЕРЕПЛАН
  1. Пересобрать сессии на сегодня и позже, прошедшие не трогать.
  2. Отдать diff с последствиями и предупреждениями.
вход факт · отклонения · форма
цифры стаб
есть —
нет lib/plan_adjust.py возвращает пустой diff; lib/season_replan.py архивирует и мержит season_plan без sanity-check.

5 · Развилки
1. Достижимость — шаг внутри планировщика или отдельный вход?
A — Шаг внутри: планировщик один, вердикт возвращается как часть ответа по макро.
B — Отдельный вход: сперва спросить «достижима ли цель», потом строить макро.
что меняет: Меняет API планировщика и то, откуда берётся потолок формы: свой расчёт или внешний сервис.
2. Макроплан — артефакт в хранилище или производное?
A — Артефакт: записан и хранится, версии видны.
B — Производное: считается из Goal + атлета + правил, пересчитывается при смене VDOT.
что меняет: Меняет границы Хранилища, появляется версионирование и пересчёт; сегодня макро написано руками — оба варианта это чинят.
3. Хранилище — одно общее состояние сезона или отдельные по подсистемам?
A — Одно: Season как корень, всё внутри.
B — Раздельно: профиль · среда · план · факт — свои репозитории.
что меняет: Меняет офлайн-снапшот (что кэшируем в клиенте) и разрешение конфликтов команд.
Замечания по текущему состоянию
Диаграмма DOMAIN-SPEC.html всё ещё подписывает блок факта как «Garmin / Stryd / TrainingPeaks» и содержит строку «поздно пришедшая активность меняет закрытую неделю» — обе расходятся с подтверждёнными I14 и I23.
Связь план↔факт зафиксирована в домене (Workout.actual_id ↔ ActualSession.linked_workout_id), но в данных её нет ни в одной таблице state — это дыра реализации, а не модели.
weekly_macro покрывает 28 недель из 49; фазы с заданными границами — только run_base … run_taper (W1–W28), триатлонные фазы без диапазонов.
