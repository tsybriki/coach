# 04 · Хостинг

Уровень: физический. Отвечает на вопрос «как приложение доступно дома и снаружи».

## Условия на этой машине

Проверено на хосте `hermeshome`:

- IPv4 `91.64.222.245` — публичный адрес провайдера, входящие соединения за NAT (проброс портов
  на роутере не настроен и не подтверждён).
- IPv6 `2a02:8109:b501:6200:...` — публичный, без NAT, входящие соединения работают.
- `tun0` `10.18.4.169` — WireGuard-туннель провайдера для обхода блокировок. Наш, не наш
  интерфейс: `wg show` пуст, своих WG-интерфейсов нет.
- `wg` установлен, `tailscale` и `cloudflared` — нет.
- `sudo` без пароля нет; есть `systemctl --user`.
- Пользователь в группе `docker` — контейнеры запускаются без sudo.
- Активные пользовательские сервисы: `hermes-gateway.service` и его варианты — то есть
  пользовательские сервисы systemd работают, автозапуск есть.

Два вывода из этого: **проброс портов на роутере недоступен** (нет управления роутером),
и **пользовательские systemd-сервисы и docker использовать можно**.

## Варианты

### A · Cloudflare Tunnel + домен на Cloudflare

```
телефон → https://coach.example.com → Cloudflare → туннель → 127.0.0.1:8080 (BFF)
```

- Наружу смотрит только Cloudflare, порты на роутере открывать не нужно, IPv4/NAT не важны.
- HTTPS и сертификат — автоматически, от пользователя ничего не требуется.
- Доступ из дома: `http://192.168.178.43:8080` напрямую, без туннеля — быстрее и без зависимости
  от внешнего сервиса.
- Минусы: трафик идёт через чужой сервис; Cloudflare Tunnel для личного использования бесплатен.
- Что нужно: `cloudflared` (не установлен), домен на Cloudflare (есть ли — не проверялось),
  либо `trycloudflare.com` — без домена, но адрес меняется при рестарте.

**Рекомендую этот вариант** как основной: не требует ни прав на роутере, ни sudo, работает
с текущим NAT, даёт нормальный HTTPS.

### B · Tailscale

```
телефон → tailnet → 100.x.y.z:8080 (BFF)
```

- WireGuard-меш, свой сервер не нужен, доступ только для устройств в tailnet.
- Наружу не выставлено ничего — максимальная приватность, но и максимальная закрытость:
  чтобы зайти с чужого телефона, устройство надо добавить в tailnet.
- Что нужно: `tailscaled` (не установлен), аккаунт Tailscale.
- Хорош как дополнение к A: доступ извне через туннель без публичного домена.

### C · WireGuard вручную + свой сервер

```
телефон → WireGuard → домашний роутер → BFF
```

- Полный контроль, ничего не светится наружу.
- Нужен VPS с публичным IP для координации либо доступ к роутеру для проброса UDP.
- Что нужно: настроить `wg-quick` (бинарник есть), открыть порт на роутере — **а это
  сейчас невозможно без доступа к роутеру**, либо поднять VPS.
- Больше ручной работы и обслуживания, чем A.

### D · IPv6 напрямую + Cloudflare DNS-прокси

```
телефон → https://coach.example.com → Cloudflare (прокси) → [AAAA] → BFF по IPv6
```

- Публичный IPv6 есть, входящие соединения работают без NAT.
- Cloudflare-прокси скрывает реальный адрес и даёт TLS.
- Минус: работает не везде — часть сетей (мобильные операторы, чужие Wi-Fi) IPv6 не имеет.
  Как основной канал — плохо. Как запасной — годится.

### Сводка

| | Наружу | Дома | Нужно поставить | Обслуживание | Вердикт |
|---|---|---|---|---|---|
| **A Cloudflare Tunnel** | да, домен | напрямую, быстро | `cloudflared` | минимум | **основной** |
| **B Tailscale** | нет, только tailnet | напрямую | `tailscaled` + аккаунт | минимум | **дополнение** |
| **C WireGuard вручную** | нет | по VPN | VPS или доступ к роутеру | много | отложить |
| **D IPv6 напрямую** | да, но не всем | напрямую | ничего | минимум | запасной |

Рекомендация: **A как основной, B как запасной для обхода проблем с Cloudflare**,
D включать не нужно — лишний канал, который надо поддерживать.

## Как это ложится на процессы

```
systemd --user:
  coach-app.service       BFF (uvicorn), restart=on-failure
  cloudflared.service     туннель, restart=on-failure
```

Пользовательские сервисы работают на этой машине — автозапуск и перезапуск при падении
получаются без sudo и без системного root.

## Конфигурация

`~/.config/coach-app/`:
```
config.toml     порт, хост, путь к данным, режим деградации
token           токен доступа (chmod 600)
```

`cloudflared` читает свой конфиг из `~/.cloudflared/config.yml`, там же credentials для туннеля.
Секреты не в репозитории.

## Что снаружи видно

Наружу — только BFF: маршруты API, `/health` без данных. Домен, Garmin, календарь, нарратор,
файлы состояния наружу не выходят. Наружу отдаются только то, что сам пользователь запрашивает
у себя: план и факт.

## Риски и что с ними делать

| Риск | Что делаем |
|---|---|
| Утечка токена | HTTPS обязателен; токен в заголовке; ротация одной командой |
| Cloudflare недоступен | B продолжает работать локально, приложение внутри дома не ломается; Tailscale как обходной путь |
| Провайдер сменил IPv4 | Дома адрес меняется — приложение на телефоне обновляет адрес; при A внешний адрес не зависит от домашнего |
| Данные на диске дома | Бэкап `data/` ежедневно, 14 копий (см. `02-хранилище.md`) |
